# APOS v1.0 and AFGS

APOS and the AI Founder Governance Stack (AFGS) are separate architectures with different primary units.

| APOS | AFGS |
|---|---|
| Project-scoped operating architecture | Three-pillar governance architecture |
| Organizes project instructions, methods, routing, state, evidence references, artifacts, and handoffs | Integrates AI Founder OS, EASGF, MDGR, and shared governance infrastructure |
| Primary question: how should persistent AI-assisted project work be organized and continued? | Primary question: how should business operation, AI-system governance, and material-decision governance interact? |
| May use a governance binding when a project reaches a material decision | Provides one candidate governance binding for APOS |

Canonical AFGS responsibility model:

```text
AI Founder OS → operates the business
EASGF        → governs the AI system
MDGR         → governs material decisions
Shared substrate → binds and enforces their interaction
```

APOS does not redefine these jurisdictions. In an AFGS-bound project, APOS can package project readiness, artifact/evidence references, requested action, and current state for the applicable AFGS governance path. AFGS remains the owner of its own verdict and execution semantics.

Therefore:

```text
APOS readiness ≠ AFGS verdict
APOS artifact validation ≠ execution permission
```

AFGS is optional for APOS. A project may bind another governance service or remain within ordinary project-level checks when no material governance layer is required.
